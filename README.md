# Chess OOP

Учебный проект по разработке шахмат на Python с использованием объектно-ориентированного программирования.

## О проекте

Цель проекта — закрепить знания ООП на практике, самостоятельно спроектировав и реализовав модель шахматной игры.

Проект разрабатывается с нуля в рамках изучения Python и ООП.

## Цели обучения

- Проектирование классов и объектов.
- Инкапсуляция и управление состоянием объектов.
- Наследование и полиморфизм.
- Композиция и взаимодействие объектов.
- Разделение ответственности между компонентами программы.
- Написание и организация тестов.

## Эволюция проекта

### 1. Переход от плоского списка ходов к системе лучей

На начальном этапе методы фигур возвращали плоский список координат возможных ходов.

Например, ладья генерировала все потенциальные клетки по четырём направлениям в одном списке.

В процессе реализации игровой логики обнаружилась архитектурная проблема: плоская структура не сохраняла информацию о направлениях движения фигуры. Это усложняло обработку препятствий, поскольку при встрече с другой фигурой необходимо прекращать движение только в соответствующем направлении, продолжая проверять остальные.

**Принятое решение:** перейти к представлению ходов в виде списка лучей.

Теперь каждый луч представляет отдельное направление движения фигуры и содержит последовательность клеток в этом направлении (от ближней к дальней). Конь и король возвращают по лучу из одной клетки на каждый прыжок, пешка возвращает один луч вперёд.

Это позволяет:
- Независимо обрабатывать каждое направление.
- Прекращать движение по конкретному направлению при встрече с препятствием.
- Корректно реализовать перемещение ладьи, слона и ферзя.
- Сохранить единый подход к генерации ходов разных типов фигур.

### 2. Разделение ходов и атакованных клеток

Фигуры знают только геометрию (`get_possible_moves`) и ничего не знают о доске. Блокировки учитывает `Game`, у которого есть доступ к доске.

Выяснилось, что «куда фигура может пойти» и «какие клетки она атакует» — разные вопросы:
- пешка ходит вперёд, но атакует по диагоналям (в том числе пустые клетки);
- ходы нельзя использовать для проверки шаха.

**Принятое решение:** два отдельных метода в `Game`:
- `get_pseudo_legal_move` — ходы по геометрии, блокировкам и взятиям, без учёта шаха;
- `get_attacked_squares` — клетки, которые контролирует фигура (нужны для проверки шаха).

### 3. Проверка шаха через симуляцию хода

Вместо отдельной логики для каждого правила (связанная фигура, король под шахом, защита от шаха) используется одна проверка: каждый псевдолегальный ход временно выполняется на доске, затем проверяется, атакован ли король своего цвета, и ход откатывается.

Так три правила решаются одним механизмом, а новые типы ходов (взятие на проходе, рокировка) смогут пройти ту же проверку.

## Структура проекта

```
chess/
└── src/
    ├── main.py
    └── game/
        ├── board.py    # доска 8x8, хранение и перемещение фигур
        ├── pieces.py   # классы фигур, геометрия ходов
        └── game.py     # правила: блокировки, шах, легальные ходы
```

## Запуск

```
python src/main.py
```

Сейчас `main.py` содержит только проверочные вызовы `get_legal_move` на стартовой позиции. Игровой цикл ещё не написан.

## Статус

Готова модель доски и фигур, генерация ходов с блокировками и взятиями, определение шаха и запрет ходов, оставляющих короля под боем. Дальше: очерёдность ходов, превращение пешки, мат и пат, затем взятие на проходе и рокировка.
